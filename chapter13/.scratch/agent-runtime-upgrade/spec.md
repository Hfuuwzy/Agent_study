# Spec: Agent 运行时升级（Run 状态机 + SSE 真实进度 + 显式降级）

**Status: ready-for-agent**

## Problem Statement

当前的智能旅行助手是一个"能跑通但不可信"的演示：编排是单一方法内固定顺序的 4 步调用，任何一步失败都会走伪造兜底——为任意城市生成以北京为基准的假坐标与占位景点，API 恒定返回成功，用户无法分辨真实数据与降级数据；前端进度条是计时器模拟的假进度，最坏要干等 50 分钟；景点图片搜不到时默认展示北京天坛照片，与目的地不符。作为求职`AI Agent 方向实习`的作品集项目，它需要能讲明白的"现代 Agent 系统"特征——真实状态、真实进度、失败可见、数据可信——同时保持简单、可运行、零新增依赖与零写盘。

## Solution

在不动 Agent 内核（保留 SimpleAgent + 高德 MCP）的前提下，为现有流水线加一层**应用级 Run 编排外壳**：

- 一次旅行请求对应一个 **Run**（唯一 `run_id` + 显式状态机），后台执行、SSE 实时推送真实进度，前端假进度条下线；
- 每步独立重试（指数退避、上限控制），失败步骤不拖垮已完成步骤，整体走向 `success | degraded | failed` 三态终局；
- **显式降级取代伪造兜底**：降级运行的响应携带失败清单（`warnings`），页面如实渲染，不再出现假坐标与错城市图片；
- 中间结果**类型化**：景点/天气/酒店搜索结果经 Pydantic schema 校验后再组装进规划提示词，不再裸拼 Agent 文本；
- 附带 5 条黄金评测集 + 离线可跑的评测脚本，全部走同一条公开 HTTP 测试缝。

## User Stories

1. 作为旅行用户，我希望提交请求后立即收到 `run_id`、页面秒回，而不是干等数十分钟，以便知道系统已受理我的请求
2. 作为旅行用户，我希望看到基于真实运行状态推送的进度（如"正在搜索景点""正在查询天气"），以便不再被假进度条误导
3. 作为旅行用户，我希望任一步骤失败时进度如实反映失败，以便我能知道发生了什么，而不是看到虚假的"生成中"
4. 作为旅行用户，我希望当计划是降级产物（部分数据缺失）时页面明确标注并说明哪一步失败，以便我能判断结果的可靠程度
5. 作为旅行用户，我希望降级结果不再包含"以北京坐标冒充目的地"的假数据，以便结果至少不会误导行程决策
6. 作为旅行用户，我希望景点图片搜不到时看到中性占位图或"示意图"标注，而不是一张与目的地无关的北京天坛照片
7. 作为旅行用户，我希望非法输入（缺日期、天数与日期区间矛盾）在请求层快速被拒绝，以便不浪费一次无效的 Agent 运行
8. 作为旅行用户，我希望某个外部服务超时只重试该步骤，而不影响已经成功的其他步骤，以便计划尽可能完整
9. 作为旅行用户，我希望单步重试有上限，超限后系统整体优雅降级或明确失败，以免无限挂起
10. 作为开发者，我希望控制台能看到每一步的状态、耗时与错误信息（loguru），以便不写任何日志文件即可定位问题
11. 作为开发者，我希望能在无网络、无真实 Key 的情况下离线跑 5 条评测集（桩实现驱动），以便随时回归验证
12. 作为开发者，我希望评测脚本对每条样例给出明确的 PASS/FAIL 与失败原因输出，以便快速判断改动是否引入回归
13. 作为开发者，我希望恶意输入（诱导泄露 system prompt / 注入指令）被隔离、不进入规划提示词，以便演示基本的 prompt 安全边界
14. 作为开发者，我希望模型输出 schema 非法经重试仍失败时系统显式 `failed` 而非伪造成功，以便诚实呈现失败
15. 作为开发者，我希望编排步骤与 Agent 提示词解耦（步骤经依赖注入构造），以便测试可注入桩、未来可演进新版步骤
16. 作为开发者，我希望升级后项目不新增任何写盘行为、数据库或第三方依赖，以便保持"可运行、可讲明白"的作品集定位
17. 作为开发者，我希望同一评测流程带真实 Key 时也能跑真实 happy path，以便最终验收真机效果
18. 作为旅行用户，我希望行程编辑/导出（草案→确认）沿用现有交互，Agent 只负责产出草案，以便升级不破坏已有功能
19. 作为求职者，我希望 README 能用状态机、事件流、失败语义三张图讲清系统，以便面试时讲得明白
20. 作为求职面试官，我希望看到这个项目在失败路径上也有明确行为（降级/重试/失败），以便判断候选人对 Agent 工程的理解深度

## Implementation Decisions

- **Agent 内核不动**：保留 `SimpleAgent` 作为单步执行器，提示词、工具注册、共享高德 MCPTool 均不改写；升级只构造外层 Run 编排（ADR-0002）。
- **不引入任何编排框架**：不迁移 LangGraph / OpenAI Agents SDK；"可替换性"仅作为面试论述（状态模型可映射到图结构），不实现适配器。
- **运行时工厂 + 依赖注入（使能改造）**：现 LLM / 高德 MCP / 编排器均为进程级全局单例，升级为按 Run 构造、依赖可注入（LLM、AMap 工具、Unsplash 均可替换为测试桩）。这是"测试缝 = 公开 HTTP API"成立的前提。
- **Run 生命周期（进程内,内存 registry,零落盘）**：状态机为 `pending → running →（步骤事件）→ success | degraded | failed`。每步携带状态/耗时/错误；单步重试采用指数退避 + 最大重试次数，仅重试失败步骤（ADR-0003）。
- **执行模型**：请求受理与执行分离——`POST` 立即返回 `run_id`（受理），Run 在后台执行；前端经 SSE 订阅该 Run 的事件流；原 50 分钟 Axios 长等待取消。
- **事件协议（向前的公开契约）**：SSE 事件类型含 `run_started / step_started / tool_call / tool_result / validation_error / run_completed`；`run_completed` 携带终态 `status`（success/degraded/failed）与 `warnings`。
- **显式降级**：命中兜底或部分失败时，终态必须为 `degraded` 或 `failed`，`warnings` 列明失败步骤与原因；不得返回无标注的成功（ADR-0001）。兜底不生成假坐标。
- **图片兜底规则**：无景点图片搜索结果时使用中性占位图或明确标注"示意图"，禁止复用与目的地不符的城市照片。
- **中间结果类型化**：景点/天气/酒店步骤的输出经 Pydantic schema 校验后进入规划上下文组装；prompt 组装基于类型化结果，不再拼接裸 Agent 文本。
- **请求层校验**：日期合法性、`start_date/end_date/travel_days` 一致性等交叉校验放在 API 层，非法输入直接拒绝（评测集样例 2 的依据）。
- **提示词安全边界**：`free_text_input` 等用户自由文本与工具返回内容按不可信数据处理；进规划提示词前做长度/指令隔离（不引入重型 guardrail 依赖）。
- **控制台诊断**：loguru 结构化输出每步状态/耗时/错误，`run_id` 作为贯穿标识；不写日志文件、不新增依赖（它还顺带修复"进程全局副作用"病灶——多 worker 部署隐患）。
- **前端**：删除计时器假进度，改接 SSE 事件渲染真实步骤；终态按 success/degraded/failed 三态渲染；编辑/导出（草案→确认）保持原样。
- **并行化（可选，排最后）**：景点/天气/酒店三搜索经 `asyncio.gather` 并发；不阻塞其余交付物。
- **文档**：根 README 章节表刷新至 Ch13；chapter13 README 增补"升级"段落（状态机/事件流/失败语义三图）。

## Testing Decisions

- **好测试的定义**：只测外部行为——公开 HTTP 契约与终态语义，不断言状态机内部实现细节。断言对象为：HTTP 状态码、SSE 事件序列、终态 `status`/`warnings`、`TripPlan` 结构与*不含伪造坐标/错城市图片*约束。
- **唯一测试缝（最高层）**：后端公开 HTTP API，经 FastAPI TestClient + 注入桩运行时（fake LLM / fake AMap MCP / fake Unsplash）驱动。所有自动化用例走此缝。
- **评测集 5 条（黄金样例）**：
  1. happy path：上海 3 天全流程 → `success`，结构完整（带真实 Key 可实测；默认桩可离线）
  2. 缺日期字段 → 请求层拒绝（非 Agent 运行期错误）
  3. 搜索返回空结果 → `degraded` + `warnings`，页面可渲染
  4. 模型输出 schema 非法 → 重试仍失败 → 显式 `failed`（不伪造成功）
  5. 恶意输入（诱导泄露 system prompt / 注入指令）→ 被隔离，不进规划提示词
  - 评测脚本：场景 JSON → 进程内请求 → 控制台逐条 PASS/FAIL + 原因；不写盘。
- **先例**：chapter13 应用树内目前无任何测试基建，本 spec 建立的 API 缝测试即首个先例，供后续修复/章节沿用同一缝；前端不做自动化（人工冒烟），超出实习项目定位。

## Out of Scope

- 认证、授权、多用户、分享链接
- 部署上线（Docker Compose / 云服务 / CI/CD）
- 任何持久化：数据库、事件落盘、日志文件（ADR-0003）
- 通用编排抽象 / 可插拔执行器 / LangGraph、OpenAI SDK 适配器（ADR-0002）
- 框架迁移与 Agent 提示词重写
- 前端自动化测试（UI 人工冒烟）
- 导出功能改进、新增 Agent（餐厅/交通）、路线规划等教程建议方向
- 第十二章式系统性评估框架（仅落地 5 条黄金样例）
