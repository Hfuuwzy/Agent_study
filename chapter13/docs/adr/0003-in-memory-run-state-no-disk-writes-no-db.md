# 0003 — Run 状态驻留进程内存，不落盘、不引入数据库

## 状态

已接受。

## 背景

一次旅行请求对应一个独立 Run。项目需要在请求执行期间保存状态机、步骤事件、工具结果与错误，以支持后台执行、SSE 实时进度和运行诊断；同时，本项目定位为一次性使用、可运行且可讲明白的实习作品集，不需要多用户历史、跨进程恢复或审计能力。

最初考虑过用 SQLite 持久化 Run 状态，也考虑过只把事件追加写入 JSONL，以便失败后复查和展示完整 trace。两种方案都会引入存储位置、生命周期、清理与一致性问题；JSONL 虽然不需要数据库，本质上仍是运行时写盘行为，与项目已经确认的零写盘边界冲突。

## 决策

Run 状态机与事件流完全驻留进程内存，由 run registry 管理：

- 不写 JSONL 或其他运行时文件；
- 不引入 SQLite、Postgres 或其他数据库；
- 不实现跨进程恢复、历史 Run 重放或为未来存储预留的 repository 抽象；
- 使用现有 loguru 控制台日志输出实时步骤、耗时与错误，便于运行期间排查和面试演示；
- SSE 的事件历史只服务于当前进程内的迟到订阅与重连，不构成持久化记录。

## 理由

- 用户每次询问 Agent 都是一次独立 Run，进程重启后恢复旧 Run 没有当前产品价值。
- 内存 registry 已满足后台执行、真实进度和显式失败语义，继续增加存储不会改善核心演示目标。
- 零写盘避免新增文件、清理策略、并发写入和部署路径等额外复杂度。
- 控制台日志足以展示真实 trace；需要复查时应在运行期间保留终端输出，而不是为此改变运行时架构。

## 被否决方案

### SQLite / Postgres

可支持跨进程恢复、查询与审计，但需要 schema、连接、迁移和生命周期管理，复杂度与当前一次性使用定位不匹配。

### JSONL 事件落盘

实现成本低于数据库，也能保留失败 trace，但仍会产生运行时文件，并带来路径、轮转、清理和敏感工具结果留存问题。因此不作为折中方案采用。

### 为未来存储预留 repository 接口

当前没有第二种存储实现或近期需求，提前抽象只会增加间接层。未来确有多用户、重启恢复或审计需求时，再通过新的 ADR 重新设计。

## 代价与已知限制

- 进程重启会丢失进行中及已完成的 Run 状态。
- 无法在应用内事后查询或重放历史运行。
- 多进程部署时，各进程的 registry 相互独立；当前单进程学习与演示场景接受该限制。

以上代价均已接受，并应在项目说明或面试讲解中如实陈述。

## 重新评估条件

只有出现多用户历史、跨进程恢复、合规审计或长期运行分析等明确需求时，才重新评估持久化方案；届时应新建 ADR，而不是在本决策下静默加入写盘行为。
